# Milestone M1: the controller learns to stop before one wall

Plan `RESEARCH-R6-PLAN.md`, section 4, row M1. A short GPU run with the real walker inside the action term, on
one wall layout and no sensor impairments. It is the first evidence that the whole chain (scene, rays, 1343-wide
observation, residual command, Pollen's walker, rewards, Beta head, PPO) learns anything, before the 1,500-iteration
runs of M2 and M3.

Everything below was run on CPU with smaller numbers (section 5); nothing here has run on a GPU.

## Before the run

- This repository installed on the DGX (`uv sync`). Where it sits next to `/opt/robotics/microduck_rl` is the
  homelab's call (plan step S1); it needs Pollen's `microduck_rl` at `0daab160` (pinned in `pyproject.toml`) and nothing
  else outside the lock.
- Pollen's walker file, sha256 `ce894d30...` (policies v10, `velstand.onnx`), at the path in `MICRODUCK_WALKER_ONNX`
  (default `~/.cache/duck-sim/policies/current/velstand.onnx`). The task refuses to start without it.
- A GPU window announced to the homelab as the plan says (about 0.5 h including the two swaps). The run itself is
  about 0.2 to 0.3 h; the per-iteration time on the GB10 is not measured (the plan's estimate is 3.2 to 4.5 s).

## The commands

The task is `Mjlab-Nav-OneWall-MicroDuck`: both wall slots abut into one 1.8 m wall across the approach, 0.6 to 1.0 m
ahead of the robot; the other six slots are parked behind and beside it; the goal is 2.6 m ahead; the ToF has no
impairments (no noise, bias, dropout, latency, mount pitch or height draw). The zone grid is the task default,
`mixed` (each environment draws Pollen's equal-angle or NVIDIA's pinhole grid at every reset).

Smoke, 64 envs for 20 iterations (does it start, does the first checkpoint land):

```bash
MICRODUCK_WALKER_ONNX=/path/to/velstand.onnx uv run train Mjlab-Nav-OneWall-MicroDuck --env.scene.num-envs 64 --agent.max-iterations 20 --agent.save-interval 10 --agent.logger tensorboard
```

The run, 4096 envs for 200 iterations:

```bash
MICRODUCK_WALKER_ONNX=/path/to/velstand.onnx uv run train Mjlab-Nav-OneWall-MicroDuck --env.scene.num-envs 4096 --agent.max-iterations 200 --agent.save-interval 50 --agent.logger tensorboard
```

Why the two flags (`MICRODUCK.md` lessons): `--agent.logger tensorboard` because W&B stops the run without a key;
`--agent.save-interval` because rsl_rl does not save when a run is stopped. With an interval of 50 the checkpoints land at
iterations 0, 50, 100, 150 and the last one (`model_199.pt`) at the end of the run. Each checkpoint is written with its
`model_N.onnx` beside it (`(1, 1343) -> (1, 3)`, the normaliser inside). Output goes to
`logs/rsl_rl/microduck_nav_one_wall/<timestamp>/`, with TensorBoard events in the same directory.

On a machine without a GPU add `--gpu-ids None` (that is how the CPU runs below were made).

## What "done" means

All three, from the plan's row:

1. Mean forward progress goes up: `Episode_Reward/progress` in TensorBoard rises over the 200 iterations.
2. Collisions go down: `Episode_Termination/obstacle_collision` falls.
3. The replayed policy stops before the wall.

For 3, replay the last checkpoint (any machine, CPU is enough; it runs the ONNX next to the checkpoint, the file that
deploys):

```bash
uv run python -m microduck_nav.replay logs/rsl_rl/microduck_nav_one_wall/<timestamp>/model_199.pt --num-envs 16 --steps 600
```

An environment counts as stopped before the wall when, in the replay, it has no obstacle contact over 0.1 N, did not
fall, closed at least 0.25 m of its initial clearance to the wall, and moved slower than 0.03 m/s over the last two
seconds. The milestone is met when at least 80 % of the replay environments do (exit code 0; the last line printed is
a JSON summary). These thresholds are this repository's choice, not NVIDIA's or the plan's; change them in
`src/microduck_nav/replay.py` if the operator wants others.

Arrival at the goal is not part of M1. At the speed Pollen's walker gives (about 46 % of the request, C3), 20 s of
walking covers about 1 to 2 m, so the 2.6 m goal is out of reach in an episode; `goal_arrival` stays 0 here.

## How the replay relates to the training

The replay builds the task's play config (16 envs, robot facing +x, no pushes) and the same observation, so a policy that
learned to brake in training should brake there. It is deterministic (the Beta mean, with the brake guard), unlike the
training rollouts, so a policy can look worse in training than in replay.

## CPU dry run

`tests/test_m1_dry_run.py` runs the smoke command at 16 envs x 5 iterations on CPU (`--gpu-ids None`), then the
replay of its last checkpoint on 4 envs for 150 steps. Result: the command trains, saves `model_0` and `model_4`
with their ONNX, and the replay prints its table and verdict; the 5-iteration policy has 0 of 4 stopped before the
wall, no collision, final speed about 0.15 m/s. That shows the chain runs end to end, not that it learns. The C7
check (`docs/CHECKS.md`) times 8 envs x 50 iterations on CPU at 2.6 s per iteration.

Zone grid options for any run: the default is `mixed`; add `--env.scene.sensors.10.grid equal_angle` to pin Pollen's
grid or `--env.scene.sensors.10.grid pinhole` for NVIDIA's (index 10 is the ToF sensor; confirmed by a CPU run with `pinhole`,
which wrote `grid: pinhole` into `params/env.yaml`).
